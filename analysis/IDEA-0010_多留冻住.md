## 方法

- **f127**：CDPruner 在 LLM 之前留 127 个（同一条 DPP 贪心顺序，前 64 个就是 CDPruner-64 的），按原顺序、连续编号；在 ShortV 为 LLaVA-1.5-7B 选的 19 层（0、2、3、12、17～31）冻住这 127 个：它们保持该层的输入状态，不算注意力输出与 MLP，其他 token 照常把它们当 key / value（预填充时缓存，生成的 token 也看得到）。按结构算的 FLOPs（文字 token 也计入）是 CDPruner-64 的 1.00 倍（冒烟测试的提示上 1.0016）：冻住的 token 每层只算 K、V 投影，约为完整计算的 1/6。
- **对照**：b127（同样 127 个、不冻住，FLOPs 1.51 倍）；f64（CDPruner-64 冻住同样 19 层，0.75 倍）；b64 = CDPruner-64（EXP-0039）。
- f127 − b64 回答“同样的计算量下，多留再冻住是否更好”；f127 − b127 是 127 个时冻住的代价；b127 − b64 是多留本身的增益；f64 − b64 是 64 个时冻住的代价。

## 机制与预测（推断，只为事后对照，不是判据）

- 64 档剩下的缺口多是信息不够：VQAv2 计数 +5.18、其他 +3.21，GQA 属性 +5.31、二选一 +10.76（F101；位置题另是编号的问题，F89）。多留 token 应当补回一部分：文献 128 对 64，CDPruner +1.2 / +1.3、DivPrune +1.9 / +1.9（各自的评测划分，SC）。预测 b127 − b64 约 +0.8～+1.5。
- 冻住的代价：ShortV 在 576 个时冻住这 19 层只掉 0.8 / 1.0（SC）。留得少时，每个 token 承担的信息更多，冻住可能更伤，也可能因为 token 少、层间变化小而更轻。预测 f127 − b127 约 −0.3～−1.0，Q1 约 0～+1。
- 若 Q1 为正：同样的计算量下“token 数”比“每个 token 算多深”更值钱，可以作为方法；若 Q2 代价大：ShortV 的层表（576 个时选的）不适合剪枝后的模型，可另立预注册按剪枝后的模型重选层。

## 相近工作与新颖性

- ShortV（arXiv 2504.00502，ICCV 2025）：冻住视觉 token 的做法本身来自它；它只与 FastV（K = 2、R = 50%）叠加来再省计算（Table 5），没有在同样的 FLOPs 下把省下的计算换成更多 token（主代理读 HTML 版正文核实，SC）。
- VScan（PAPER-0014）：撤掉第 16 层起的全部视觉 token 并多留到 128 个，GQA −5.6（P20）：撤掉，不是冻住。
- 其他（WebSearch 标准模式 5 次，2026-10-31）：V-Skip（2606.08511，跳过注意力块）、STAR-Pro、VisionDrop、TOPS（按层改 token 数）都不同。没有找到“多留 + 冻住、FLOPs 对齐”的做法（UN：检索有限，写进论文之前要做系统查新）。

## 风险与边界

- 视觉部分的 KV 缓存是 CDPruner-64 的 2 倍（冻住的 token 每层仍有 K、V），解码时每步多看 63 个 key；要同时报告。
- 本流程中冻住的实现是“整层算完再把图像行还原”（输出与只算 K、V 相同，check_freeze），每题秒数不会变快；计时要等只算 K、V 的实现。
- 层表取自 ShortV，不在本项目的数据上调；剪枝后最合适的层可能不同。
- 开发集多次使用（P14），任何结论都要在新数据上确认；IDEA-0008 的教训：要在 MME、POPE 上检验推广。

## 为什么这样做

- **K = 1 很便宜**：层平均预算 64 时，第 0 层看全部 576 个只占 576 / 32 = 18 个名额，之后 31 层各留 47 个（(576 + 31 × 47) / 32 = 63.5）。在确认集上，K = 1 的路由（47 个）与 VisionZip-64（64 个）持平或更好：VQAv2 test3 −0.02，GQA testdev +1.62（F56）。
- **两种排序各有所长**（EXP-0028，开发集）：
  - 开放式题（不路由的题）上，VisionZip 的排序好：VisionZip-64 + 覆盖 16 − FastV K = 1 + 覆盖 16 为 +2.43 [+1.14, +3.72]（VQAv2）/ +0.19（GQA）；
  - yes/no 与计数题（被路由的题）上，K = 1 的题目查询路径好：FastV K = 1 路由 − VisionZip-64 为 +2.34 [+1.04, +3.62] / +1.67 [−0.44, +3.70]。
  - FastV 第 0 层的注意力有位置偏差（F16、EXP-0006；VScan 也指出早层偏向序列后部的 token），开放式题上它的排序不如编码器的 CLS 注意力。
- **拼接的线索**：被路由的题用 FastV K = 1 路由、其余用 VisionZip-64 + 覆盖 16，开发集上比 VisionZip-64 +1.96 / +1.17（探索性，EXP-0028 记录内深挖）。
- **要检验的是**：开放式题上，“一层全看 + 编码器排序”能否比“在 LLM 之前剪到 64 个”更好。如果能，两条路径可以合在同一个 K = 1 的框架里：每题都先一层全看，再按题型选排序。

## 方法（不加前向，层平均 63.5 个）

1. **第 0 层**：LLM 收到全部 576 个 patch（普通 LLaVA 的输入）。
2. **第 1 层起**：只留 47 个，按视觉编码器第 −2 层 CLS 对各 patch 的注意力（各头相加，即 VisionZip 选主导 token 的分数）从高到低取，不取整块落在填充里的 patch，不分块、不除位置先验。保留的 token 保持原来的位置编号（同 FastV）。
3. **三种变体**：
   - `k1cls`：每道题都这样排；
   - `k1qcls`：沿用 IDEA-0003 的路由：yes/no 与 how many 题走 K = 1 的题目查询路径（与 `fastv64k1_qroute` 逐题相同），其余题按 CLS 排序；
   - `k1qcls_c16`：在 `k1qcls` 的不路由题上加覆盖 16（框与 IDEA-0005 的相同；框内 = CLS 排序自己在框内的个数 + 16，框内、框外都按 CLS 分数取）。
4. **代价**：视觉编码器多返回一组注意力图（CLIP 在 transformers 4.37.2 里只有 eager 注意力，特征不变）；第 0 层不需要输出注意力图。每题秒数在 EXP-0030 中实测。
5. **代码**（在 EXP-0029 之后提交到 code/token-pruning）：
   - `fastv_llava.py`：新的 score_kind `cls` 与选项 `cls_unrouted`；视觉塔前向返回注意力图并记下每次预填充的 CLS 分数；`fastv_cls_log` 每题一条记录；
   - `run_eval.py`：`--fastv-score cls`、`--fastv-cls-unrouted`、`--fastv-cls-log`；
   - `exp0002.py`：`fastv64k1_cls`、`fastv64k1_qroute_cls`、`fastv64k1_qroute_cls_c16`（及 `_kl`）；CLS 配置自动加 `--fastv-cls-log`；
   - `check_k1cls.py`（新）、`analyze_0030.py`（新）。
   - 不加新选项时，计算与已提交的代码完全相同（check_zoom.py 的回归核对）。

## 假设与机制（推断）

- **假设**：
  - 第 0 层里，题目 token 读到全部 576 个 patch，被留下的 patch 也已（因果地）汇集了它前面的 patch，所以少留 17 个的损失能补回来；
  - 编码器的 CLS 排序没有 LLM 早层的位置偏差，开放式题上比 FastV 的注意力排序好；
  - 两者合起来，开放式题上好于 VisionZip-64，yes/no、计数题上保留 K = 1 路由的优势。
- **替代解释与风险**：
  - ①47 个比 64 个少，又没有 VisionZip 的 10 个合并 token，开放式题可能反而变差；
  - ②拼接的增益可能部分是开发集上的噪声；
  - ③CLS 排序偏向显著物体（PosPrune；EXP-0028：53 个里平均 26 个落在点名的物体上），不显著区域的题仍要靠覆盖；
  - ④第 0 层看全部 token 的作用，一部分可能来自 FastV 第 2 层之前的两层（K = 2）在 F51 中已经体现，K = 1 只是预算分配不同。

## 可检验的预测（推断，用于事后对照，不是判据）

- `k1cls` − VisionZip-64：约 −1～+1（不确定）。
- `k1qcls` − VisionZip-64：约 +1.5～+2.5（被路由的那一半约 +1.2 / +0.75，来自拼接）。
- `k1qcls_c16` − `k1qcls`：约 +0.3～+0.8。
- 所选 − VisionZip-64 + 每题覆盖 16（EXP-0028 的所选）：约 +0.5，区间可能含 0。

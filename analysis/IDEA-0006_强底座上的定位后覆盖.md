## 为什么换底座

- IDEA-0005 只在 FastV 一族（在 LLM 内部按注意力剪枝）上测过。查新指出：64 个 token 时文献报告的强方法 GQA 为 58.2～58.7，本项目的路由在 GQA testdev 上是 55.47；在低约 3 分的底座上 +1，只说明缩小了一部分差距。要说“通用的插件”，需要加在一个强底座上。
- 可用的强底座：本机已有源码、并且已核对过的只有 VisionZip（CVPR 2025，在 LLM 之前剪枝）。DivPrune、CDPruner 的源码没有下载（下载要用户许可）。
- VisionZip-64 在本项目已有的结果：VQAv2 test1 70.57、test2 70.70，GQA testdev 55.18（EXP-0018-R05、EXP-0020-R08、EXP-0022-R07）。同一数据上 IDEA-0003 的路由：VQAv2 test2 68.53，GQA testdev 55.47。所以 VisionZip-64 在 VQAv2 上比路由高约 2 分，在 GQA 上相近。

## VisionZip 怎样选 token（源码核对）

`source/VisionZip/visionzip/clip_encoder.py`：

- 在视觉编码器倒数第二层，取 CLS 对各 patch 的注意力，各头相加；
- 留 CLS 和注意力最高的 53 个 patch（“主导 token”，按原位置顺序）；
- 其余 523 个 patch 合并成 10 个“上下文 token”：等间隔取 10 个目标，其余每个按 key 的余弦归到最相近的目标，取平均后加到目标上；
- 共 64 个，经投影层进入 LLM，每一层都是 64 个。
- 主导 token 的选择不看题目。

## 方法（不加 LLM 前向，不改 token 预算）

1. **哪些题覆盖**：沿用 IDEA-0003 的路由规则，只用来决定哪些题覆盖。yes/no 与 how many 题保持 VisionZip 原样，其余题（不路由）定位并覆盖。另一种做法是每道题都覆盖（`c16all`）。
2. **定位**：与 IDEA-0005 完全相同。
   - 题目查询 q = 题目各词输入 embedding 的加权均值，权重为 IDF × 可见性；
   - 576 个 patch 的 LLM 输入 embedding（投影层作用在倒数第二层上，就是普通 LLaVA 送进 LLM 的那组）与 q 的余弦，取非填充区最高的 8 个，围出正方形框（边长 8～16，限制在图像的内容带里）；
   - 所以同一道题、同一张图，框与 IDEA-0005 的框相同（EXP-0028 的实现核对之一）。
3. **覆盖**：框内名额 = VisionZip 自己在框内的主导 token 个数 + n（n = 16 或 32，上限 53）。在框内（不含整块落在填充里的 patch）按 CLS 注意力取，其余名额按 CLS 注意力在框外取。
4. **其余不变**：剩下的 patch 照 VisionZip 的规则合并成 10 个上下文 token，共 64 个。
5. **代价**：多一次投影层（576 个 patch 过两层 MLP，约 24 GFLOPs，约为 7B LLM 预填充的 1.5%）。每题秒数在 EXP-0028 中实测。
6. **代码**：
   - `code/token_pruning/visionzip_cover.py`（新）；
   - `run_eval.py` 加 `--vz-cover` 等参数；
   - `exp0002.py` 加四个配置。
   - 没有题目查询（被路由，或可见权重为 0）时，前向与 VisionZip 逐行相同。

## 假设与机制（推断）

- **假设**：
  - VisionZip 的 53 个主导 token 不看题目，开放式题要看的区域可能分到的不多；
  - 输入层的题目查询能大致定位被问区域（IDEA-0005：定位框盖住话题物体至少一半的占 88%）；
  - 在框里多留，补上证据；框外仍留 CLS 注意力最高的那部分，保留全局信息；被挤出的 patch 还会被合并进上下文 token，不完全丢失。
- **替代解释与风险**：
  - ①集中：增益只来自把名额集中到图像中部的一块（居中框对照可以区分）；
  - ②CLS 注意力最高的 token 里有一部分携带全局信息，挪走太多会受损（覆盖 32 检验）；
  - ③VisionZip 的上下文 token 已经部分保留了框内的信息，增益可能比 FastV 一族小；
  - ④FastV 一族上，K = 2 覆盖的增益大部分来自集中（F54），VisionZip 上可能也是这样。

## 可检验的预测（推断，用于事后对照，不是判据）

- 覆盖 16 − VisionZip-64 > 0，但小于 FastV K = 2 上的 +1.51 / +0.98。
- 覆盖 16 − 居中框覆盖 16 > 0。
- 覆盖 32 不比覆盖 16 好（挪走的高注意力 token 太多）。
- 每题都覆盖时，被路由的题上的变化方向不确定。

## 最小验证

- 开发集运行 [EXP-0028](实验报告/EXP-0028_record.md)：10 次，在 VQAv2 dev2、GQA val400 上跑 VisionZip-64、覆盖 16、居中框覆盖 16、覆盖 32、每题覆盖 16。
- 选择规则、判读与实现核对在计划 v1 中写定；分析脚本 analyze_0028.py 已用替身数据空跑。
- 确认在开发之后写计划：用 VQAv2 test3、GQA testdev。VisionZip-64 在两者上都已有运行（EXP-0027-R04、EXP-0022-R07）。

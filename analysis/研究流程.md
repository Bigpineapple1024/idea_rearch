# 研究流程：从论文到 idea，再从 idea 到实现

版本 v2.0，2026-10-23。本文是本仓库**唯一的流程规范**，依据用户的方法论：「ClaudeCode 做科研焚决」第 1–3 章，以及配套文章《5 个 Skill 打通科研全流程》《科研死循环的根本原因》《跨领域论文方法迁移》。

- **v1 已归档**：此前的 SOP（v1）偏离了方法论中“制造意外实验”和“选 baseline”两处，已归档到 [archied/2026-10-23_SOP-v1_从论文到融合方案.md](archied/2026-10-23_SOP-v1_从论文到融合方案.md)，其中有用的检查清单已并入本文。
- **五个 skill 是工具，不是目的**：调用顺序与交接协议见 [五技能流程](../.claude/skills/5-skill-research-workflow.md)。skill 本身不是必需的，必需的是做到它描述的核心功能，其中最重要的是**榨干每一次实验的数据**。
- **前置条件**：项目结构和必需文档见 [README](../README.md) 与 [index](index.md)。

## 总览

```text
第一章 从论文到 idea
  ① 选 baseline → ② 复现（门槛：能复现才往下走）→ ③ 解析论文（含源码核验）
  → ④ 制造意外实验：组合实验 → 记录 → 榨干 → 更新现象台账
  → ⑤ 深挖意外现象：反复走 1a–2b，直到根因
  → ⑥ 骨架全景图 × 改进内容交叉分析
  → ④⑤⑥ 循环，直到找到一个最容易突破的现象

第二章 从 idea 到实现
  ⑦ 选改进方向 → ⑧ 深挖到算子级 → ⑨ 找领域 B（通常偏理论）的解决方案
  → ⑩ 找领域 C（应用）的迁移案例 → ⑪ 改造 baseline，让方法的生效条件成立
  → ⑫ 验证：A / A′ / A′+B，再走 1a–4b 的 3a–4b

贯穿全程：每一次实验（包括复现）都走 record → squeeze → 更新台账 → 回流 deep-read
```

## 第一章 从论文到 idea

### ① 选 baseline

- **候选标准**：近两年引用量最高、有源码的论文。理由有三：
  - 引用量高，大概率有源码；
  - 基于它改进的论文多，方便后面“制造意外实验”时组合；
  - 也方便统计骨架上哪些位置被改造过。
- **衍生工作多不是硬条件**：找不到满足这一条的 baseline 也问题不大，只影响第 ⑥ 步的骨架改造统计，不影响制造意外实验。
- **引用量要注明来源和查询日期**。
- **本项目当前的选择**（DEC-0011）：视觉 token 剪枝选 FastV；时序预测选 DUET。其余论文作为组合实验的素材和对照方法。

### ② 复现：能复现才进入下一步

- **复现标准**：
  - 评测结果确定的（如 LLaVA 贪心解码）：与论文或官方结果相差不超过 1 个点。
  - 有训练随机性的（如时序模型）：至少跑 3 个种子，论文报告值落在“均值 ± 2 倍标准差”之内。
- **复现不上时**：按“环境 → 数据 → 配置 → 实现”的顺序排查。一周内仍复现不上，就换候选清单里的下一篇，并在 version-evolution 记一条决策。不在复现不了的 baseline 上做改进。
- **复现也是一次实验**：写 EXPERIMENT_RECORD（`source_idea_id: none`）和 SQUEEZE_REPORT。复现中发现的现象同样登记到台账。

### ③ 解析论文

1. 用 MinerU 把 `papers/` 里的 PDF 解析到 `literature/processed/<paper_id>/`。
2. 用 analyze-paper 生成论文笔记（ANALYSIS_PACKAGE），写到 `analysis/论文笔记/`。笔记要包含：
   - 核心任务、方法架构、关键贡献、实验结果；
   - 与自己实验的关系、论文中发现的现象；
   - 优缺点、可借鉴的内容、核心总结。
3. **有源码就必须读源码**，逐条写进笔记的 E 表：
   - [ ] 方法核心在哪个文件、哪几行；实际做法与论文描述是否一致。
   - [ ] 写死的常量：层号、长度、路径、`.cuda()`、prompt 长度等。
   - [ ] 预算或口径的定义（例如“保留 64 个 token”是输入数还是层平均）。
   - [ ] 版本差异：arXiv 各版本、会议版、代码分支、环境变量开关。
   - [ ] batch size、padding、KV cache、注意力实现等限制。
   - [ ] **评测协议**：测试集是否全部计分（有没有 `drop_last=True`）；超参数、早停、模型选择是否用到了测试集；划分和归一化统计量是否只来自训练集。
   - [ ] **推理是否确定**：eval 模式下是否还有随机采样；报告了几个种子。
   - [ ] 许可证、依赖版本、安装方式是否真的可用。
   - [ ] 论文说了、代码里找不到的东西。
4. **取不到全文时**：作者主张标为 SC，写明“待回查原文”，不能当成已核实。

### ④ 制造意外实验

1. 用 deep-read 批量分析论文，输出“问题—现象”交叉矩阵（MODE_C_PACKAGE）。核心逻辑：**论文 a 的问题能否被论文 b 的现象解决**。根据矩阵组合不同论文的方案做实验。
2. **随机组合同样允许**（第 3 章）：组合的前提不一定是“a 的问题能被 b 的现象解决”，也可以把两篇独立、无关联论文的方案融合起来，做没人做过的实验，去发现两篇论文都没发现的问题或现象。
   - 这类实验标为“探索性组合”。
   - 它的目的是产生现象，不是直接产出论文方法，所以这一步**不要求先做新颖性检索**。
   - 新颖性只在第二章提出最终方法时检查。
   - 不能凭组合本身声称新颖性或因果关系。
3. 组合实验同样遵守下文的“实验执行规范”：先跑 A、B 各自单独的效果，再跑 A+B；控制预算；所有运行都登记。
4. **每次实验后都要做**：
   - 用 record-experiment 记录事实；
   - 用 squeeze-experiment 尽可能榨干数据，输出实验报告；
   - 把发现的现象写进 [已发现的实验现象](已发现的实验现象.md)，值得写进论文的写进 [论文素材库](论文素材库.md)；
   - 把新现象交给 deep-read 回流，更新矩阵。

### ⑤ 深挖意外现象

- 对 squeeze 发现的现象走 1a–2b（见附录一），用 [1a-4b 模板](templates/1a-4b机制分析.md) 记录。
- 走完一轮后继续追问：“这轮分析有哪些新发现？其中哪些值得继续研究？”针对新发现再走一轮。
- 反复多轮，尽量把问题从表面现象挖到具体模块、运算机制，直到算子层。
- AI 给出的因果解释必须用代码和实验验证；没验证过的因果边一律标为“假设”。

### ⑥ 骨架全景图 × 改进内容交叉分析

- **两份文档**：维护 [baseline骨架的全景图](专题分析/baseline骨架的全景图.md)（对 baseline 各结构已了解什么、还不知道什么）和 [所有论文在baseline骨架的改进内容](专题分析/所有论文在baseline骨架的改进内容.md)（各篇论文改了哪里、改了什么）。
- **交叉分析**两份文档，就能看出：哪些地方被反复改造，哪些地方很少有人改、甚至没人改过。
- **怎么解读**：
  - 被改造得多，说明这里存在很大的问题，**不能说明这里已经没有创新空间**。
  - 完全没有被改造过的地方，大概率没有需要改造的问题，很可能是“无解”的地方，深入研究也难以找到改进点，优先级放低。
- **何时进入第二章**：不断循环 ④⑤⑥，对 baseline 的了解会越来越透彻，积累的实验现象也越来越多。这时找一个**最容易突破**的现象开始解决，就进入第二章。

## 第二章 从 idea 到实现

### ⑦ 选改进方向

- **两个因素**：解决后会不会大幅提升，以及这个问题好不好解决。两者一般互斥，按自身实际情况取舍。
- **普遍性检查**：问题可能只在某个数据集上存在，换一个数据集就没了。选之前至少在第二个数据集或设置上确认问题仍然存在。
- **多个候选排队验证时，按成功可能性排序，不按“只需改几行代码”排序**。改动小只说明试错便宜，不说明方案可能成立。排序依据从高到低：
  1. 问题是否真实存在，且在当前 baseline 上造成了可测的损失（有本项目的实验证据，并且有改进空间）；
  2. 相近设置中，同方向的修正是否被证明有效；
  3. 机制能否给出单一方向的预测（“可能变好也可能变差”的方案，可能性低于方向明确的）；
  4. 预期效应是否大于噪声和实际意义阈值（受影响的部分占比太小，即使机制对也可能测不出来）；
  5. 成本：只在前四项相当时，才用来决定先后。
- 证据不足以判断时，先做能估计成功可能性的诊断（例如先拆分 baseline 的损失落在哪些子任务上），而不是先做最便宜的方案。
- 每个候选写明“成功可能性：高 / 中 / 低”和理由；排序变化记入 version-evolution。

### ⑧ 深挖到算子级

为选定的方向建一份 1a–2b 分析文档，反复深挖，直到落到算子级问题。深挖过程中往往还会出现新的实验现象，按第 ④ 步登记。

### ⑨ 找领域 B 的解决方案

1. **怎么检索**：用 ⑧ 得到的底层问题和机制描述去检索，**不要只用本领域的任务关键词**。要找的是“解决问题的机制相同或相似”的论文，任务可以完全不同。领域 B 一般是偏理论的领域。
2. **核对原文**：确认它确实研究了这个问题，而不只是在摘要或引言里提到类似概念。
3. **用 1a–2b 深入分析，回答三个问题**：
   - 这个方法最初是为了解决什么问题？
   - 它通过什么机制解决的？真正起作用的是哪一部分？
   - 它需要哪些条件才能生效？（最重要，例如依赖的输入特征、数据分布、模型结构、训练目标）

### ⑩ 找领域 C 的迁移案例

- **找什么**：检索是否有领域 C（和你一样偏应用）已经把领域 B 的方法用到了自己的任务上。
- **对比 B 与 C**：
  - C 是直接用原方法，还是改了输入输出结构？
  - 有没有调整网络连接、训练目标或其他机制？
  - 哪些改动是为了适配任务，哪些可能是方法生效的必要条件？
- **找不到 C**：不代表不能迁移，只是要承担更多验证工作。

### ⑪ 改造 baseline，让方法的生效条件成立

- **思路**：不是“怎样修改 B 的方法，把它塞进 A”，而是“能不能改造 A 的 baseline，让它具备 B 方法生效所需的条件”。
- **记录**：用 [跨领域迁移方案模板](templates/跨领域迁移方案.md) 写清楚：B 的每个条件、A 是否满足、C 如何适配、A 需要怎么改造、怎么检查条件已经成立、要付出什么代价。

### ⑫ 验证：到底是谁带来了收益

- **至少比较三组**：
  - A：原始 baseline。
  - A′：只做结构适配。
  - A′+B：适配后再加入领域 B 的方法。

  可行时再加 A+B，看适配是否必要。
- **怎么读结果**：A 与 A′ 的差异，说明结构适配本身是否有效；A′ 与 A′+B 的差异，才说明 B 的方法在新系统中是否带来收益。
- **两个都要看**：目标问题有没有改善，整体指标有没有稳定提升。
- **最后走 1a–4b 的 3a–4b**（附录一），确认改动符合第 2b 步的问题分析。

## 实验执行规范（每一次实验都适用，包括复现和组合实验）

1. **实验前写清楚**：
   - 这次要回答的一个问题；
   - 预计改善什么，哪些指标可能受影响，最后看哪个整体指标决定去留；
   - 什么结果算成功，什么结果出现就停；
   - 最迟在什么结果出现后回退，回退后哪些观察值得保留。

   有 IDEA 包时写在 IDEA 包里；复现和探索性组合写在实验记录的“计划”一节。
2. **一次只改一个变量**。能拆开验证的就拆开：先验证 A，再验证 B，最后决定是否组合。怀疑有交互时，比较 baseline、仅 A、仅 B、A+B 四组。
3. **测试集只用于最终评测**：调参、早停、模型选择只看验证集；测试集所有样本都要计分（不允许 `drop_last=True`）。
4. **重复与不确定性**：
   - 有训练随机性的实验，默认 3 个种子（2021、2022、2023），作为论文主结论的实验用 5 个；报告均值和标准差。
   - 评测确定的实验（贪心解码），用按样本 bootstrap 估计置信区间。
   - 单个种子的结果不作结论。
5. **预算上限**：
   - 一个 idea 的试验阶段最多 30 次运行或 20 个 GPU 小时；
   - 一个 baseline 的复现最多一周。

   超出就停下来复盘，并在 version-evolution 记一条。上限可以调整，但要在实验前写明。
6. **局部改善不等于整体收益**。指标不动时，要区分以下几种情况，不能只写“没涨”：
   - 假设不成立；
   - 实现没有生效；
   - 生效条件不满足；
   - 测量不够灵敏；
   - 噪声或变量间的交互。
7. **不打补丁**：每加一个新机制，先回答三个问题：
   - 它要解决的是哪一个问题？
   - 如果整体指标不改善，最迟在什么结果出现后回退？
   - 回退后哪些观察值得保留？

   系统越来越复杂、整体指标却始终不升时，就回退；不因为已经投入了很多时间而继续补救。
8. **每次实验都要有明确结论**，哪怕是负结论，并写清“这次实验后我们多知道了什么”。上一次的结果没弄明白之前，不急着改下一版。
9. **优先借鉴已有论文中经过验证的解决方法**，而不是从零设计新机制。

## 五个 skill 在流程中的位置

```text
analyze-paper → deep-read（Mode C）→ discover-innovation → 实际执行 → record-experiment → squeeze-experiment → 回流 deep-read
```

- **对应关系**：
  - ③ 解析论文用 analyze-paper；
  - ④ 的矩阵和回流用 deep-read；
  - 第二章中把选定的方向写成可执行方案用 discover-innovation；
  - 每次实验之后用 record-experiment 和 squeeze-experiment。
- **禁止跳步**（摘自交接协议）：
  - 不能跳过矩阵，从论文分析直接生成 idea；
  - 不能把实验记录中的单次结果直接当成新机制，必须先 squeeze，再交 deep-read；
  - 不能把 squeeze 报告直接当成 idea 卡片。
- **每次交接包的元数据都要齐全**；材料不足时标为 `partial` 或 `unknown`，并在 `missing_evidence` 中写明怎么补。
- **squeeze 每次都做**：目的是从一次实验里榨取尽可能多的知识；结果不理想、没有差异、出现异常时同样要做。

## 运行产物、编号与备份

- **编号**：全项目统一递增，不按方向分开：
  - 论文 `PAPER-xxxx`
  - 矩阵 `MODE_C-xxxx`
  - 想法 `IDEA-xxxx`
  - 实验 `EXP-xxxx`，单次运行 `EXP-xxxx-Rnn`
  - 决策 `DEC-xxxx`
- **每次运行必须留存**，放在 `code/output/<EXP>/<RUN>/`：
  - `cmd.txt`：完整命令行；
  - 配置快照；
  - `git.txt`：代码 commit 和 `git diff` 补丁；
  - 外部仓库的 commit；
  - 随机种子；
  - `env.txt`：环境导出（`conda env export` 或 `pip freeze`）；
  - `nvidia-smi` 输出（显卡、驱动、CUDA 版本）；
  - 完整的 stdout/stderr 日志；
  - `metrics.json`；
  - 必要时保存预测与真值文件；
  - 以上所有文件的 `sha256sum` 清单。
- **备份**：实验室电脑 D 盘（WSL 下为 `/mnt/d/idea_rearch_backup/<EXP>/<RUN>/`）。实验记录中写明备份路径和校验和；只有本机路径不算可恢复。
- **登记**：所有运行（包括失败、中断）登记到 [experiment-results](experiment-results.md)。

## 分支与提交

- **main**：`analysis/`、`paper/` 和各类文档，直接在 main 上修改。
- **实验分支**：每个方向一个，`code/token-pruning`（视觉 token 剪枝）和 `code/ts-forecasting`（时序预测），存放实验代码和运行。核验过的实验报告同步到 main，并写明实验代码的确切 commit。
- **提交与推送**：由 Claude Code 负责，每次提交后立即推送。

## 附录一：1a–4b 完整流程

| 阶段 | 做什么 |
| --- | --- |
| 1a | 观察所有失败实验的现象 |
| 1b | 把发现的现象归类，看哪些现象指向同一个根因 |
| 2a | 对归类后的现象不断追问，找更深层的原因 |
| 2b | 把追问结果建成因果链，逐层描述问题出在哪里 |
| 3a | 替换 2b 中找到的有问题的模块，验证是否有效 |
| 3b | 有多个改动时，改动之间应当相互独立、互不影响 |
| 4a | 开始消融：逐个加入模块，验证单模块效果，量化每个模块的收益 |
| 4b | 再次验证第三阶段的改动是否符合第二阶段的问题分析 |

**阶段门槛**：某一阶段的数据不理想，就回退到上一阶段重新走。只有对上一阶段几乎做到完全了解，才进入下一阶段。

“完全了解”的可操作标准：上一阶段的关键问题都已有证据回答，或者已写明为什么当前无法回答，以及需要什么证据才能回答。

注意：1a–2b 产生的是假设，不是因果证明；AI 给出的连贯解释也不能证明根因。

## 附录二：论文定位（a–d 级）

| 级别 | 定位 |
| --- | --- |
| a | 提出新问题，并用新颖的方案解决 |
| b | 用新颖的方案解决已知问题 |
| c | 把其他论文中的方案直接用到自己的论文中 |
| d | 只对已有论文做微调 |

这只是内部描述，不是录用标准。

## 附录三：a–b 级创新方法论

- **a 级**：用现有系统做出一件意料之外的事，不断追踪、验证这个现象，就可能发现一个全新的问题（对应第 ④⑤ 步）。
- **b 级**：本领域面临的问题在别的领域也存在，借鉴别的领域是怎么解决的（对应第 ⑨–⑪ 步）。
